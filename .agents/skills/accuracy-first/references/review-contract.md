# 对抗式 Review 契约

## 输入（原实现者提供，独立审查者必须读）
- 原始需求（不要用实现摘要替代）
- 允许的改动范围与禁止触碰区域
- 不变量及关键影响链
- 完整 Git Diff（含可能影响本次变更的已有改动的说明）
- 相关文件与必要代码上下文
- 已运行验证的证据与未运行项

## Review 顺序
1. 复述真正要求改变和不能改变的行为。
2. 独立定位原始代码路径，检查改动是否落在正确位置。
3. 以生产事故为假设倒推三个最有可能的失败场景。
4. 逐一核对调用方、合法与非法输入、错误分支、状态副作用、权限/安全边界。
5. 只提交能定位到具体文件/符号/行为的发现；把未知明确标注为“需验证”，不要臆测 Bug。

## 缺陷报告格式

- P0：可能导致严重数据破坏、资金/安全事故或明显不可接受的生产风险。
- P1：核心需求未满足、明显回归、权限/重要状态处理错误。
- P2：边界条件遗漏或重要的可维护性/兼容性风险。
- P3：非关键优化建议；默认不要因为 P3 扩大修改范围。

逐项输出：`[P级别] 文件:行号/符号 | 失败条件 | 证据 | 最小修复建议 | 确认度(已证实/待验证)`。
未发现问题时输出 `NO FINDINGS`，并列出检查范围与剩余盲区；不得宣称“绝对没有 Bug”。
P0/P1 未解决应阻断放行。审查者保持**只读**，不私自修改代码。

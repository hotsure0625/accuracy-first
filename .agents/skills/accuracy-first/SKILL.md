# Accuracy First v1.0 — 高正确率代码修改

## 目标与边界

优先级：**行为正确与安全 > 可审查的最小变更 > 最少验证成本 > 速度**。
目标是减少人工测试和冗余测试，**不是免除必要验证**，也不能保证“一次修改百分百正确”。
适用：既有仓库的 Bug fix、局部功能修改、静态扫描整改、业务维护。
不适用：纯讲解、无改码任务；大型重构与架构迁移需另立计划及更完整验证。

## 强制步骤（不得跳过，不必每步向用户请示）

### 0. 确认边界和工作区
- 阅读用户需求、仓库规则 `AGENTS.md` / `CLAUDE.md`、目标分支及 `git status`。
- 列出已有未提交修改，不要覆盖、清理或擅自纳入用户已有更改。
- 从需求抽取：期望改变的行为、明确不改变的行为、禁止改动的文件/范围。
- 识别足以影响正确性的缺失输入；无法消除关键歧义时澄清，不可猜测实现。

### 1. 证据驱动调查（先只读，后改码）
- 检索真实入口、调用链、相关实现、现有测试、错误路径与接口契约。
- 必须把“看到的代码事实”与“推测”标记区分；记录关键文件与符号。
- 说明根因或待证实假设；若证据不足，继续最低成本调查。
- 不根据方法名称、注释或熟悉的框架惯例脑补未读的实现。

### 2. 锁定不变量与风险等级
- 列出最重要的**不变量**：输入输出、API 契约、鉴权、异常类型、状态迁移、数据库副作用、幂等性、兼容性（选适用项）。
- 用 `references/risk-gates.md` 的 LOW / MEDIUM / HIGH / CRITICAL 判断风险：看影响，不看修改行数。
- 对资金、权限、安全、敏感数据、数据迁移、并发一致性默认 HIGH 或 CRITICAL。
- 设定 Test Budget Gate：必须验证的内容、可暂缓的内容、预算、停止条件和不可接受风险。

### 3. 设计最小改动并反证
- 从满足需求的方案中优先选修改面最小、依赖最少、可解释性最高的方案。
- **改前列出三个最可能推翻方案的反例**；按实际适用性检查空值、空数据、非法输入、重复调用、权限、异常、并发和状态不一致。
- 不为消除扫描告警而降低安全检查、扩大白名单、忽略异常或跳过必须的权限校验。
- 未能守住关键不变量的方案不得进入实施阶段。

### 4. 实施最小 Diff
- 仅修改与需求有关的文件和代码；不要顺手重构、重命名或全仓格式化。
- 每处修改都必须能够映射至问题根因、明确需求或必要的安全约束。
- 不得擅自 force push、提交/发布、修改部署配置或把测试结果写成未实际执行的 PASS。
- 不要碰未授权的历史文件、无关工程或用户现有更改。

### 5. 对抗式审查（优先独立上下文）
- 提供审查者：**原始需求、关键不变量、风险等级、实际 Git Diff、相关代码路径和验证结果**，不要先提供实现者的自我辩护。
- Claude Code 如存在 `.claude/agents/accuracy-critic.md`，优先委托这个只读子 Agent。
- Codex 如具备独立子 Agent/会话能力，委托独立审查；否则可在当前会话执行反证式复核，**但必须标注“非独立审查”**。
- 重点检查：修错位置、调用方遗漏、边界错误、权限绕过、异常处理变化、行为回归和无关 diff。
- 对审查反馈按 `references/review-contract.md` 处理；修正后重新检查受影响部分，不无限次重复审查。

### 6. 最低充分验证与交付门禁
- 所有等级至少查看 `git diff`、`git diff --check` 和变更范围；允许使用 `scripts/inspect_diff.py` 辅助，但其结果**只证明 Git 格式检查，不证明行为正确**。
- 先选最便宜的确定性验证，再根据风险追加编译、类型检查、静态扫描、单元/集成/端到端验证。
- **低风险不等于零验证；高风险不能仅靠 Prompt 自我审查放行。**
- 不可运行的检查标记 NOT RUN 并说明原因；测试失败标记 FAIL；不允许把未运行标记 PASS。
- 若 CRITICAL/HIGH 缺失必需的证据：可交付代码草案，但明确 BLOCKED / NEEDS VERIFICATION，禁止宣称可安全发布。

## 输出格式（保持简洁）

1. **问题与证据**：根因/假设 + 文件/符号。
2. **修改内容**：变更文件、每处改动的必要性、未触及范围。
3. **不变量与反例**：列出关键契约、反例结论。
4. **Review**：独立 / 非独立、发现的问题及处理结果。
5. **验证清单**：实际执行的命令、PASS/FAIL/NOT RUN；分清静态检查和运行时验证。
6. **最终状态**：READY FOR REVIEW / BLOCKED / NEEDS VERIFICATION；指出残留风险及下一项最低成本检查。

不要输出自评“99% 正确”或编造已运行的命令。
